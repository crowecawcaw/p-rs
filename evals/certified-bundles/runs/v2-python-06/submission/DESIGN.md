# Certified change bundles design

The service stores a single small root record and immutable content-addressed trie nodes through the durable key/value store. The root contains pointers to four maps: branch heads, bundles, submit idempotency responses, and publish idempotency outcomes. Each map is a persistent hash trie keyed by the SHA-256 digest of its string key. A trie update writes a new leaf and the path back to its root; unchanged nodes remain shared. This bounds each stored record independently of the number of bundles and outcomes, while the root stays constant sized.

Every state-changing operation reads the current root version, computes its changes against that root, writes any new immutable nodes, and then CASes the root once. That root CAS is the operation's linearization point. Failed CAS attempts leave unreachable immutable nodes and retry from the latest root. A response lost after the root CAS is recovered by retrying: submit and publish consult durable idempotency maps, while approve is set-valued and duplicate-safe. Other mutations are linearizable even if a caller whose response was lost has to inspect status before choosing a new operation.

The root CAS commits all related records together. In particular, publication makes every head change, the bundle's published marker, and the publish request outcome visible in one step. Rejected publish outcomes are also memoized at the same point. Head reads capture one root and follow only pointers reachable from it, giving a consistent snapshot even during concurrent publication. Bundle revisions, approvals, CI results, and heads are always recomputed after a root CAS race, so unrelated Service instances coordinate solely through the store.

Initial heads are installed lazily by constructing the initial head trie and CASing an empty root. Concurrent first use may build the same immutable nodes; only one root initialization wins and the others use the winner. Constructors perform no store I/O. Immutable node keys are hashes of their canonical compact JSON, so a retry can reuse a previously written node after an interrupted write. The implementation assumes SHA-256 collision resistance and that records for a referenced immutable node remain available. It uses no external I/O, process-wide coordination, background work, or mutable cache.
