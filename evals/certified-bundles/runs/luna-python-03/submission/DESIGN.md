# Certified change bundles design

The service stores an append-only event history as immutable records and uses one small durable root key as the commit pointer. Each record contains a previous-record key, an event kind, and its payload. Record keys are SHA-256 hashes of canonical JSON, so callers can safely prepare records before trying to publish them. Initialization adds a genesis record with the initial heads and installs its pointer with compare-and-swap.

Every mutation first reads the root and reconstructs the state by following immutable records back to genesis. It then applies the operation's decision rules and prepares a record. The record is written with CAS at its content-derived key, then the root pointer is changed with CAS against the version read earlier. A failed pointer CAS leaves an unreachable immutable record and causes the operation to reread and retry. Unreachable records have no effect and need no cleanup. A caller that loses a response after root CAS can retry; the root already exposes the committed event. Submit checks the original submit event, so retries return the revision-1 digest even after revisions.

The root pointer CAS is the linearization point for every committed mutation. Publishing stores its request outcome and the `applied` flag in one event. Replaying that event both updates every target head and marks the bundle published, so heads and the memoized result have the same visibility point. Rejected publish outcomes are also events, making retries by request ID return the original outcome. Status and head reads capture one root pointer first and replay only that immutable prefix; that root read is their snapshot point.

All mutable state is derived from committed records, so restarts need no recovery procedure beyond replay. The event log records approvals, current CI results, revisions, and publish outcomes; replay clears approvals and CI on revision and applies only successful first publications. All JSON returned from the store is treated as a copy, and inputs and outputs are copied to avoid mutable aliasing.

The design deliberately serializes commits through one root key. This simplifies atomic multi-branch publication and progress under contention, at the cost of write throughput and replay work growing with history. Records are immutable and retained indefinitely. The implementation assumes each individual input/event fits the store's 16 KiB value limit, as required by this record layout; the tested workloads use small branch maps and bundle payloads.
