# Mutation checking and exploration diversity findings

## What diversity means today

Snappea already has several schedule exploration signals, but they answer different questions:

- The activity report is event/state activity coverage: state machines and monitors, received/sent events, and observed transition links. It is explicitly modeled as event/state activity in [coverage.rs](../../crates/snappea/src/checker/coverage.rs), with sets of received/sent pairs and graph links in [coverage.rs](../../crates/snappea/src/checker/coverage.rs). It does not count P assertion sites or source lines.
- Scenario coverage tracks whether attached scenarios were reached/satisfied and the distinct abstract timelines satisfying them. The report data is in [engine.rs](../../crates/snappea/src/checker/engine.rs); successful satisfaction is recorded per schedule around engine lines 772–785.
- Timeline abstraction provides per-receiver pairwise (default), k-gram, causal, and hybrid representations, and optional payload hashes in [timeline.rs](../../crates/snappea/src/checker/timeline.rs). Feedback strategies use timeline tokens as their diversity signal, and the report counts distinct abstractions.
- Feedback-guided scheduling deduplicates exact timeline strings, scores a new one by its MinHash distance from the most similar saved timeline, then retains/mutates schedule and input generators. See [feedback.rs](../../crates/snappea/src/checker/feedback.rs) and [feedback.rs](../../crates/snappea/src/checker/feedback.rs). It also boosts novelty when a scenario makes progress. This is exploration diversity, not a measure of test adequacy or assertion coverage.
- Existing state hashing is a separate repeat-state pruning signal used by selected strategies, not source coverage or semantic test quality.

The check driver turns on activity coverage by default and writes `coverage.txt`, while bug outputs include schedule and trace artifacts. [driver/check.rs](../../crates/snappea/src/driver/check.rs) configures this, and lines 570–608 write bug traces, coverage, and summary. The current summary has counts/time/depth, but no mutation results.

## Assertion and line coverage

There is no assertion-site or source-line coverage counter in the checker. There is also no direct way to report “these assertions were evaluated/passed” or “this branch was taken.” Coverage today is at the model event/state graph level. The observed-log monitor coverage is likewise explicitly monitor states, handlers, and transitions, not P model paths; see [observe_coverage.rs](../../crates/snappea/src/checker/observe_coverage.rs).

The semantic IR retains spans: every compiled statement and expression has a `Span` (file ID plus byte offsets), and assertions are explicit `StmtKind::Assert { cond, message }` nodes. See [program.rs](../../crates/snappea/src/sema/program.rs) and [program.rs](../../crates/snappea/src/sema/program.rs); [span.rs](../../crates/snappea/src/syntax/span.rs) defines byte ranges, and [span.rs](../../crates/snappea/src/syntax/span.rs) maps registered sources to line/column. Thus line mapping is available during compilation, but runtime coverage does not currently preserve/assert which span was executed. A source-level mutation can map to original files and lines if it retains source names and records its edit spans.

## Two automatic checks with different meanings

Keep automatic reachability probes separate from semantic implementation mutation. They answer different questions and must not share a “mutation score.”

**Reachability sentinel:** automatically place a uniquely named `assert false` at one selected user handler (or assertion body), then run the original test case. If Snappea reports that sentinel, the handler was exercised in at least one explored schedule. If the baseline passes but the sentinel version also passes, the point was not reached in the explored schedules. This is a useful quick diagnostic for vacuous models; it is not evidence that the handler is incorrectly unreachable, because it may be intentionally unreachable or outside the search bound.

**Implementation mutation:** preserve the user’s assertions/specification byte-for-byte and mutate implementation behavior only: for example, perturb a guard, swap a comparison boundary, skip an assignment, or weaken a precondition in the P machine/model. A mutant is killed when the unchanged spec/assertions find a bug. This asks whether the model’s contract detects a plausible implementation defect. Mutating or removing the assertions themselves is usually unkillable by that same suite: fewer/weaker assertions usually make the variant pass, so it cannot be the primary adequacy score. If assertion edits are ever included, present them only as separate experiments about property sensitivity.

For an ordinary `snappea check` model, a user’s P assertions and monitor specs are the oracle, and P implementation machines are the subject. The checker does not mutate arbitrary Python/Java/application code. The existing Python/JVM/Go/Rust integrations record application events and check those against P monitors; mutation of an external application needs an external test runner that feeds its mutated behavior to Snappea, so it should not be implied by a core `check` feature.

## Feasibility, cost, and limits

A reachability sentinel can be introduced in a temporary source copy and checked by the normal driver. The typed IR has explicit `StmtKind::Assert { cond, message }` nodes and retained spans; registered source files map byte ranges to line/column, see [program.rs](../../crates/snappea/src/sema/program.rs), [span.rs](../../crates/snappea/src/syntax/span.rs), and [span.rs](../../crates/snappea/src/syntax/span.rs). This makes AST/IR instrumentation safer than naive source insertion. A source-copy prototype also works but must insert after local variable declarations (P rejects statements before declarations), preserve project inputs, and remap temp paths in diagnostic output.

One sentinel proves reachability of one point if that marker is the reported failure. Inserting sentinels at every point at once does not report complete coverage: the first reached sentinel terminates that schedule. The simplest reliable implementation checks one target per run, which costs about one bounded model check per target. A better eventual implementation instruments runtime/compiled IR with a per-point hit bitset and reports the points observed over the same schedules; that avoids N repeated runs and does not abort at the first hit. Existing event/state activity coverage may already answer some handler-reachability questions, but it does not identify arbitrary source assertion/line execution.

The bounded checker creates false negatives for reachability: a handler might be reachable only after more schedules/steps, under a different seed, or under an input choice not explored. Always label a pass as “not reached within this search budget.” A false alarm can arise if the marker is reached in an intended/benign handler; that is a useful reachability fact, not a model bug. Ignore the marker result if the run fails for another assertion/timeout; require the unique sentinel text in the bug report. Multiple-worker output and first-bug stopping mean per-point runs are easier to interpret than a large batch.

Semantic mutations cost at least one bounded check for each variant, plus parsing/type-checking if source is edited. Use a small automatic deterministic default sample and a global campaign deadline; stop each mutant after the first counterexample. Report generated, invalid (parse/type-check failure), killed, survived, timed-out/inconclusive, and skipped counts separately. A survivor means only “not killed under this run’s search budget.” It may be equivalent, unreachable, not detected by the unchanged properties, or merely missed. Do not call the killed/valid ratio “coverage” or “mutation score” without a well-defined, curated operator set and equivalent-mutant handling. Preserve mutant ID, operator, original source location, seed, schedule/step/time budget, and per-mutant counterexample artifacts.

An opt-in broad campaign can add comparison flips, boundary changes, guard/assignment edits, and control-flow changes. Type-check all variants before scheduling. Keep the original spec unchanged and make each mutation isolated. Equivalent or invalid mutants must not be silently removed from the denominator; report them as distinct statuses or explicit suppressions. Source text edits should be applied right-to-left and preserve original file names in diagnostics where possible. Each mutant needs its own output directory because Snappea-style check outputs fixed bug file names that are replaced per run; see [driver/check.rs](../../crates/snappea/src/driver/check.rs).

## Small frozen-v1 probe

I ran an automatic sentinel insertion prototype outside the repository with the frozen v1 evaluation models and the bundled Snappea v0.1.0 executable. The prototype copied the model, inserted `assert false, "reachability sentinel: eCommit";` into the first syntactic `eCommit` handler, then invoked `snappea check` with the same single test, `-n 100`, and `-j 1` for baseline and sentinel variants. The source fixtures are in `evals/certified-bundles/private/calibration-p/reachability/`; `tools/probe_reachability.py` reproduces the probes automatically. Generated evidence stays local under `results/`.

| Frozen v1 model | Baseline | `eCommit` sentinel | Observation |
|---|---|---|---|
| `luna-p-05/submission/bundle_model.p` (the vacuous model; `BundleStore` declares an `eCommit` handler that is never sent to) | Pass, 100 schedules, 0.00 s | Pass, 100 schedules, 0.00 s | The sentinel is not reached. This matches the review finding that `BundleStore` sends `eCommit` to `Publisher`, while no message reaches `BundleStore`’s handler. |
| `luna-p-03/submission/Bundle.p` (the nonvacuous atomic-publish model; `Server` announces `eCommit` on a successful publish and `CommitChain` observes it) | Pass, 100 schedules, 0.00 s | Fails after 1 schedule, 0.00 s, with the unique sentinel at `mutant.p:79:7` | The handler is exercised and the report includes a replayable `bug.schedule`. |

The first naive insertion in the vacuous model landed before `var result: bool` and failed parsing (`extraneous input 'var'`), because P requires local declarations before statements. Moving the sentinel after the declaration made the mutant valid and produced the pass shown above. This is direct evidence for AST/IR instrumentation or declaration-aware source edits, not blind text replacement. The nonvacuous failure is meaningful only because the failure names the sentinel; otherwise a pre-existing unrelated bug could be mistaken for a reachability hit.

These two examples establish that the basic signal distinguishes a known vacuous handler from a known reached event handler on these small models. They do not establish completeness, a useful default budget for larger systems, or an implementation-mutation score.

## Incremental recommendation

For a small agent-useful default, add an automatic quick reachability diagnostic during `check`: instrument a bounded set of assertion/handler points using hit bits in the compiled runtime, run with the same exploration as the user’s check, and report “reached” or “not reached within N schedules / T seconds.” Keep ordinary verification’s exit status governed by the original model and tests; reachability status is diagnostic because a not-reached handler may be intentional. If hit-bit instrumentation cannot land in the first slice, use one target sentinel per bounded run for a small number of assertions only, and expose the cost clearly.

Then add an explicit opt-in `--mutations` campaign for semantic implementation mutations, preserving specs/assertions unchanged, with deterministic selection, strict global budget, isolated artifacts, and clear killed/survived/invalid/inconclusive statuses. Before increasing its default, measure overhead on small bundled examples and ensure existing found-bug traces remain replayable. Assertion weakening/removal remains outside the primary campaign.
